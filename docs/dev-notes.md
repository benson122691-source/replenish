# 開發手記（草稿）— ReplenishAI

> 這是依目前真實進度起草的版本。投稿前請用你自己的話改寫，並只保留你真的理解、能在面試中解釋的內容。標「待補」的地方要等後續里程碑完成後再填。

## 01｜要解決什麼問題

中小型零售店的採購人員，每週要決定上百個品項各補多少貨。常見做法是用 Excel 移動平均，結果旺季缺貨、淡季積壓。而且「預測準不準」和「實際多花多少錢」之間沒有被連起來看。

我想做一個工具：預測未來 28 天銷量，把預測轉成補貨建議，並用「持有成本＋缺貨成本」比較不同預測方法，讓人看到省多少錢，而不只是誤差數字。

## 02｜怎麼做的

- 先寫 project-brief 與 PRD/SRS/SAD/SDS/測試計畫，需求編號可對應到測試案例。
- 資料用 M5（Walmart）格式；因為環境限制，目前先用格式相同的**合成資料**開發，真實 M5 放進 `data/raw/` 就能重跑。
- 特徵：所有銷量 lag 與滾動特徵至少位移 28 天，保證預測第 1~28 天時用不到未來資料。
- 模型：LightGBM（Poisson 目標，因為銷量是非負計數），對照 seasonal naive 與 28 天移動平均。
- 補貨：order-up-to 公式 `S = μ(L+R) + zσ√(L+R)`，並用保留期的真實需求模擬庫存，計算持有與缺貨成本。
- 評估：3 個滾動原點，每個原點重新訓練、預測 28 天；加上缺貨成本比例的敏感度分析。
- API：FastAPI 提供 /health、/forecast、/replenish、/compare（M3 完成）。啟動時讀取實驗產生的 artifacts，請求時不重新訓練；每個回應都標示 data_source。
- 頁面：單一 HTML 檔（原生 JS＋內嵌 SVG 圖表，不靠外部 CDN），由同一個 FastAPI 服務提供，只呼叫 API、不自己算結果；合成資料會在頁首顯示警示（M4）。
- Docker：建置時跑一次實驗產生 artifacts，容器啟動只讀檔（M4，本機 `docker compose up` 已驗證，映像 879MB）。
- 待補：部署（M5）。

## 03｜怎麼驗證

已執行（2026-11-08，合成資料）：
- pytest 43 項全過（含 M3–M4 的 20 項 API 測試，測試會用 artifacts 重算並比對 API 回傳的數字）：資料格式、無資料洩漏、切分正確、完美預測誤差為 0、補貨公式與 MOQ、模擬守恆與成本非負、LightGBM 可重現。
- 3 個滾動原點平均：RMSSE：LightGBM 0.678 < 28 天移動平均 0.721 < seasonal naive 0.961。
- 模擬成本：LightGBM 比 28 天移動平均低 19.6%；缺貨成本比例從 0.2 到 1.6，排名都不變。完美預測（oracle）是下界。

限制（要如實寫）：
- 以上都是**合成資料**的結果，不代表真實零售表現；真實 M5 的結果待補。
- 成本參數（持有 25%/年、缺貨 0.4× 單價）是假設值，不是真實成本。
- 起始庫存、σ 的估計方式是簡化設定；沒有考慮訂購成本、在途量初始值與供應商限制。
- 頁面尚未在瀏覽器截圖留證、部署尚未完成；LLM 助理未排定。
- /forecast 回傳的是最後 28 天的回測預測（模型只用預測原點以前的資料），不是真正的未來預測。

## 04｜學到什麼

- **基準有時比預期強**：28 天移動平均贏過 seasonal naive，因為資料雜訊比星期效應大，只看上週一個值很不穩。我原本寫的測試預期相反，測試失敗時我沒有去改資料，而是改成用沒有雜訊的序列驗證實作正確。
- **防止資料洩漏要寫成測試**，而不是只靠自己小心。
- **評估不能只看誤差**：加上成本模擬後，能回答「差多少錢」，也能用敏感度分析檢查結論是否依賴我設定的假設。
- 待補：卡在哪裡、怎麼解決、如果重做會改哪一步（等 M3–M5 做完，用你自己的經驗寫）。
